### Лебедь 16

Описание события:

После проверки служба безопасности ввела правило: любые действия в продуктивной среде — только по заявке с согласованием и записью сессии. На ночных инцидентах получение доступа стало занимать около сорока минут при целевом времени реакции пятнадцать. Дежурные, чтобы успеть в сроки, начали пользоваться общими учётными записями, оставшимися со старых времён; служба безопасности это обнаружила и говорит о дисциплинарных последствиях. Обе стороны ссылаются на свои обязательства, и обе правы.

Реакция на событие:

К продуктивной среде приравниваем информационные системы и оборудование, которое используется для хранения и распространения артефактов разработки (репозиторий с релизами продукта, git с исходниками), контроллеры домена, система регистрации обращений (helpdesk), сетевое и серверное оборудование на которых находятся эти системы. Тестовая среда и среда разработки не подпадают под требование ИБ поэтому процесс работы с ними не меняется.  

Для внесения изменений в продуктивный контур (изменение конфигурации аппаратной и программной части) создаем выделенный терминальный сервер с необходимым ПО (в том числе ПО для записи сессии пользователя). На сетевом уровне закрыть прямые подключения к подуктивной среде из сетей с АРМ разработчиков. Доступы к dev и test средам остаются без изменений.  

Для в dev/test репозитории в pipline'ы добавлены шаги по клонированию в prod репозиторий, задача запускается в ручном режиме, для запуска требуется согласование от ИБ.
Для администраторов информационных систем (HelpDesk), сетевых и серверных администраторов изменения согласовываются через новый тип изменения - "Изменение конфигурации".

На локальные УЗ заменить пароли и ограничить к ним доступ в системе управления паролями. Доступ сохранить только у руководителей соответствующего направления. Разработчики и техническая поддержка используют только именные (доменные) УЗ.

Правки в регламент управления ИТ:
- Добавлен новый маршрут "Изменение конфигурации";
- Добавлена роль Специалиста по ИБ ;
- Добавлен пошаговый Маршрут согласования изменений для каждого типа изменений;
- В описание ролей указана именно роль, а не команда.


### Лебедь 42

Описание события:

Компания начала продавать сервис партнёрам под их собственными марками: партнёры сами поддерживают своих клиентов, а ваша команда становится второй и третьей линией для десяти чужих служб поддержки. У каждого партнёра свои соглашения с клиентами, свои приоритеты, часы работы и система учёта, а эскалируют они почти всё как аварию высшего приоритета. Конечные пользователи о вас не знают, но последствия ваших сбоев ложатся на партнёров, которые требуют компенсаций. Договоры с партнёрами подписаны коммерческим блоком и не содержат никаких обязательств партнёров по качеству их первой линии.

Реакция на событие:

Продуктами компании пользуются более 10 000 организаций (по данным 2024года), техническая поддержка Труконф уже сейчас выступает для них 2 и 3 линией и консультирует команды штатных сотрудников заказчика. Если договор уже подписан, значит партнеры приняли не только правила использования и распространения продукта (сублицензионный договор), но и условия технической поддержки пользователей. В соответствии с SLA не зависимо от выбранного пакета технической поддрежки штрафные санкции не предусмотрены, обязанности исполнителя и ответственность прописаны в пункте 4.1.  

Для клиентов использующих пакет поддержки Премиум добавить возможность:
* Заказать брендирование (изменение цветовой схемы и логотипа) сервера Труконф и клиентского приложения.
* Предоставить возможность выезда технического специалиста Труконф на площадку заказчика. В рамках выезда может быть проведено обучение сотрудников, разбор инцидента, контроль обновления либо применения изменений.
* Помощь в подготовке пакетов для массового развертывания, сценариев\скриптов установки и настройки продуктов компании.

Правки в SLA:
- Добавлен пункт 2.2.3. Расширяющий перечень услуг в рамках пакета поддержки Премиум
- Изменено ограничение на разработку сценариев, скриптов и иных средств автоматизации в пункте 2.3.

Правки в регламент управления ИТ:
- В Запросы на изменение добавлен тип "Стандартное изменение".
- Добавление роли "Дежурный разработчик" (участвует в согласовании стандартных изменений). 
- Скорректирована роль "Эксперт технической поддержки" (добавлен функционал реализации стандартных изменений) 
- В каталог услуг добавлены стандартные запросы на изменение "Брендирование интерфейса в корпоративный стиль" и  "Автоматизация развертывания и настройки"
